# Resolver maturation audit — August 2026

A package-by-package review of DNS Daddy focused on one question: **can an
operator tell whether this software is working, and if not, why not?**

The audit was prompted by a real failure. The maintainer deployed DNS Daddy in
a Linux VM, added their network in the dashboard, and clients could not use the
resolver. Nothing in the product said why. That failure is reproduced,
root-caused and fixed here.

Priority order throughout: correctness → reliability → security →
diagnosability → usability → performance → presentation → new features.

---

## A. Executive summary

**Overall maturity: credible alpha.** The engineering process is visibly real —
CI runs the race detector, four static analysers, container scanning, an SBOM
and an end-to-end smoke test that asserts an open-resolver configuration
*refuses to start*. Security-relevant decisions carry their reasoning in the
code. That is well above what "AI-assisted side project" usually means.

**The strongest parts.** The resolution path is disciplined: the client ACL is
checked before any other work; ANY is answered per RFC 8482 rather than
forwarded; behavioural detection is structurally incapable of changing an
answer because it runs after the response is decided; a failed or truncated
feed keeps the last known good index instead of silently emptying it. The
DNSSEC wording is careful in a way that is rare — it says "the upstream
reported AD", not "validated", because a forwarder cannot know the difference.

**The weakest part, and the theme of this audit: the product could not
distinguish "running" from "working".** Every health surface reported liveness.
None reported reachability. A resolver refusing 100% of real traffic presented
as `status: ok`, `resolverStatus: operational`, `protectedNetworks: 2` and a
green container health check. The counter that proved the problem —
`Handler.refused` — was incremented on exactly the failing path and read by
nothing outside its own unit test.

**Security concerns.** No new vulnerabilities were found. The controls that
exist are sound and are enforced by tests. The gap is assurance, not design: no
independent adversarial review has been done on the DNS parser, the resolver,
policy attribution or authentication. Static analysis is clean, which means no
rule matched — not that the logic is right.

**Reliability concerns.** The deployment artefacts had drifted from the
binary's own defaults with nothing to catch it, and that drift is what caused
the reported outage. Deployment files are now pinned to the Go defaults by
test.

**Architectural debt.** Low. The packages are small, the boundaries hold, and
there is very little of the duplicated-abstraction, dead-branch, comment-
restating-the-code texture that AI-assisted code usually carries. The one
genuine smell found was introduced during this audit and removed in it (a
sentinel-encoded optional integer, §D-6).

## B. Findings

Severity: **P0** breaks a normal deployment · **P1** wrong behaviour in a real

### F-1 · P0 · deployment — the documented install refuses every LAN client

| | |
|---|---|
| **Component** | `.env.example`, `docker-compose.yml`, `README.md` |
| **Problem** | `.env.example` shipped an *active* `DNSDADDY_ALLOWED_CLIENT_CIDRS=127.0.0.0/8,172.16.0.0/12` beneath a heading reading "REQUIRED on a public VPS". The documented first step is `cp .env.example .env`, so that value won the Compose substitution and replaced the built-in ACL — loopback plus every private range — with loopback and the Docker bridge alone. |
| **Impact** | Every client on a LAN or in a VM answered `REFUSED`, while the dashboard, `/api/v1/health` and the container health check all reported healthy. A LAN operator was led past the fix by a heading that told them it did not apply to them. |
| **Reproduction** | `cp .env.example .env && docker compose up -d`, add `192.168.1.0/24` as a Network, then `dig @<host> example.com` from that network → `REFUSED`. |
| **Fix** | Commented the assignment out and rewrote the guidance LAN-first, stating plainly that setting the variable **replaces** the default rather than adding to it. |
| **Test** | `config.TestEnvExampleDoesNotNarrowTheClientACL` |
| **Commit** | `5dee45c` |
| **Residual risk** | None for the shipped artefacts. An operator can still create this by hand — which F-3 now detects. |

### F-2 · P1 · deployment — Docker served fewer clients than a native install

| | |
|---|---|
| **Component** | `docker-compose.yml` |

### F-3 · P0 · product — a network could exist in the dashboard and be unable to resolve

| | |
|---|---|
| **Component** | `internal/api`, `internal/web`, `cmd/dnsdaddy` |
| **Problem** | "Network" and `dns.allowed_client_cidrs` are independent settings that read like one. Nothing anywhere correlated them. `allowed_client_cidrs` appeared in no API response, no dashboard screen and no health output — only a startup log line and one string in `deploy/healthcheck.sh`. |

### F-4 · P1 · observability — the counter that proved the fault was dead code

| | |
|---|---|
| **Component** | `internal/dnsserver`, `internal/api` |
| **Problem** | `Handler.RefusedClients()` counted exactly the failure the maintainer hit and was referenced by nothing but its own test. |
| **Impact** | The one number that distinguishes an ACL problem from a firewall, routing or port-conflict problem was collected and thrown away. |

### F-5 · P1 · correctness — link-local IPv6 clients were refused and misattributed

| | |
|---|---|
| **Component** | `internal/dnsserver`, `internal/policy` |
| **Problem** | The kernel reports a link-local peer with a scope zone (`fe80::1%eth0`). `netip.Prefix` carries no zone and its `Contains` returns false for *any* zoned address. Both `Handler.clientAllowed` and `policy.prefixContains` compared zoned addresses against zone-less prefixes, so every comparison failed. |
| **Impact** | `fe80::/10` ships in `DefaultAllowedClientCIDRs`, so the shipped configuration promised to serve exactly the clients it turned away. RFC 8106 RDNSS — how a router advertises a resolver — commonly advertises a link-local address, so this is a real deployment. Where a client got past the ACL it matched no network and silently took the catch-all policy. |
| **Reproduction** | `netip.MustParsePrefix("fe80::/10").Contains(netip.MustParseAddr("fe80::1%eth0"))` → `false`. |
| **Fix** | Strip the zone before the prefix comparison in both places. The zone names the interface an address was seen on, not its membership of a prefix. |
| **Test** | `dnsserver.TestClientACLAllowsZonedLinkLocalIPv6`, `dnsserver.TestClientACLStillRefusesZonedAddressOutsidePrefixes`, `policy.TestMatchClientHandlesZonedLinkLocalIPv6` |
| **Commit** | `6b9e216` |
| **Residual risk** | The same `fe80::` address can exist on two interfaces, so link-local attribution cannot distinguish them. Documented at the call site. |

### F-14 · P2 · diagnostics — a false failure on a deliberate public resolver

*Raised by automated external review of PR #33.*

| | |
|---|---|
| **Component** | `internal/diag` |
| **Problem** | With `dns.allowed_client_cidrs` empty, every configured network was reported REFUSED — so `/api/v1/diagnostics` showed a false failure and `dnsdaddy doctor` exited non-zero on a working deployment. |

### F-15 · P2 · diagnostics — upstreams were probed with a socket connect, not a query

*Raised by automated external review of PR #33.*

| | |
|---|---|
| **Component** | `cmd/dnsdaddy/doctor.go` |
| **Problem** | The `UPSTREAM` section passed against forwarders that resolve nothing, so `doctor` could report READY while every cache miss returned SERVFAIL. |
| **Root cause** | `probeUpstream` used `net.DialTimeout` and treated success as an answer. On UDP that is a local socket association: it succeeds without a packet leaving the machine, so a silent, wedged or absent resolver looked reachable. On TCP it proves a socket opened and nothing more — blind to a failed DoT certificate verification or a DoH endpoint serving something other than DNS. It also carried `upstreamDialTarget`, a second and cruder copy of spec parsing the resolver already does. |
| **Fix** | Probe through `resolver.ParseUpstream` and `Upstream.Exchange` — the resolver's own transport — and require a well-formed response addressing the question asked. `upstreamDialTarget` deleted rather than repaired: the duplicate stack was the underlying problem. `UpstreamProbe` gained `Rcode`, so `diag.Upstreams` now separates silence from reachable-but-unusable (REFUSED/SERVFAIL), whose action says explicitly that this is not a firewall. |
| **Test** | Four cases failing on the parent commit — silent UDP responder, nothing listening, silent TCP responder, DoT against a plain-TCP listener — plus a real answering server that must still pass, and `diag.TestUpstreamsTreatANonSuccessRcodeAsUnusable`. Verified live against two unroutable TEST-NET upstreams. |
| **Commit** | `9e0cb95` |

### F-16 · P2 · diagnostics — `doctor` migrated the database it promised not to touch

*Raised by automated external review of PR #33. The residual risk noted under
F-6 was understated: this is what it actually was.*

| | |
|---|---|
| **Component** | `internal/store`, `cmd/dnsdaddy/doctor.go` |
| **Problem** | Against an **existing** database, `store.Open` applies the schema, runs migrations, seeds first-run defaults and switches journalling to WAL. Running a newer binary's `doctor` against an older live deployment therefore migrated it, and contended with the daemon — from the one command whose documented promise is that it changes nothing. |
| **Fix** | `store.OpenReadOnly`: `mode=ro` so SQLite opens the file read-only and never creates it, and `query_only(true)` so any write fails rather than being attempted. `journal_mode` is deliberately not set, because setting it writes to the database header. No schema, no migrations, no seeding — if the database predates a column this binary knows about, the query fails and the caller reports that, which beats silently upgrading a deployment somebody was only inspecting. |
| **Test** | Five cases in `store/readonly_test.go`: no mutation of journalling or seed data, writes rejected, a missing database not created, a live WAL database read correctly while the daemon holds it — and `TestOpenIsNotSafeForInspection`, which pins the mutation to `store.Open` so the two cannot quietly converge. |
| **Verification** | A database left in DELETE journal mode with no seed rows was still in DELETE journal mode with no seed rows after a `doctor` run. |
| **Commit** | see branch |

## C. Why a normal VM deployment failed

Multiple mechanisms can produce "the resolver is up and my clients cannot use
it". They are listed here with how DNS Daddy now tells them apart, because the
central failure was not that any one of them occurred — it was that the
software could not say which.

**1 · The client ACL did not include the LAN.** *(the actual cause — F-1)*
The documented `cp .env.example .env` narrowed the ACL to loopback and the
Docker bridge. Every LAN client was `REFUSED` before any other work. Nothing
reported it: the refusal path writes no query-log row (deliberately — an
unauthorised source could otherwise fill the disk), the counter was dead code,
and the dashboard reported the network as protected.
*Now distinguished by:* `doctor` sends a real query and reports `REFUSED` as
"the resolver is running and declining this source address", naming the address
the probe left from and the ranges configured; the network cross-check names
both values; `dnsdaddy_client_refused_total` climbs.

**2 · A network was added, which does not grant access.** *(F-3)* The two
settings look like one.
*Now distinguished by:* a `FAIL` naming the network, its policy, its CIDRs and
the ACL, whose action begins "Adding a network assigns it a policy; it does not
permit it to resolve."

**3 · Port 53 was held by something else.** systemd-resolved binds
`127.0.0.53:53` on most Ubuntu installs.
*Now distinguished by:* when nothing answers, `doctor` tests whether the port
is bindable. Free means nothing is running; occupied means another process
holds it, named by pid via `/proc` socket inodes, with systemd-resolved,
dnsmasq, BIND, Unbound, Pi-hole and CoreDNS each given their specific remedy.

**4 · The listener was bound to loopback only.**
*Now distinguished by:* the probe target is derived from the configured listen
address, and a loopback-only listener reports `PASS` locally while the network
cross-check still shows which networks cannot reach it.

**5 · A firewall or Docker port publication blocked the path.**
*Now distinguished by:* silence versus `REFUSED`. Nothing answering points at
reachability — the check's action names firewalls and Docker port publication.
Something answering `REFUSED` rules all of that out in one step.

**6 · VM NAT rewrote the source address.** Under NAT the hypervisor gateway
replaces the client address, so every client appears as one address and
per-client attribution is impossible.
*Partially distinguished:* `doctor` reports the address its own probe left
from, which makes translation visible when run from a client. **Not yet
detected automatically** — see §F.

**7 · No usable upstream.** Everything resolves to `SERVFAIL`.
*Now distinguished by:* `SERVFAIL` is reported as "reachable but could not
resolve" and points at the `UPSTREAM` section, where each forwarder is dialled
individually. One dead forwarder of two warns; all dead fails.

**8 · Resolving but not protecting.** An empty index blocks nothing.
*Now distinguished by:* `THREAT INTELLIGENCE` fails on an empty index, and
warns — rather than failing — when last-known-good data is being enforced but
is stale, because protection has not stopped.

**The honest summary.** The most likely single cause of the reported failure is
mechanism 1, compounded by mechanism 2. Both are now fixed at source and
detected if recreated. Mechanism 6 is the one DNS Daddy still cannot diagnose
on its own.

## F. Remaining limitations

1. **No VM matrix was executed.** This session had no hypervisor. Bridged, NAT
   and host-only networking were reasoned about and are documented in §C, but
   not measured. The matrix itself is now written down as
   [deployment-matrix.md](deployment-matrix.md), with every row marked "not
   run". **Executing those rows is the most valuable next contribution to this
   project**, and the NAT rows in particular are the input a future automatic
   NAT warning would need.
2. **Docker Compose was not launched.** The Compose default is now pinned to
   the Go constant by test, which is a stronger guarantee than one manual run,
   but `docker compose up -d` was not executed end to end.
3. **NAT source-address rewriting is not automatically detected.** DNS Daddy
   sees the translated address and cannot know it was translated. A heuristic
   is plausible — many distinct clients collapsing onto one address that is a
   hypervisor gateway — and is deliberately not guessed at here.
4. **The configuration banner appears on the dashboard page only.** An
   operator who lands directly on Networks or Query log does not see it.
5. **`doctor` under Docker must be run inside the container.** Each affected
   check says so rather than reporting a false failure, but it is a sharp edge.
6. **Pi-hole coexistence is analysed but not measured.**
   [pi-hole.md](pi-hole.md) reasons from the implementation — every claim
   traceable to a named part of the code — but neither topology has been
   deployed. The page says so at the top and lists what would have to be
   measured.
7. **No performance measurement was taken.** The resource claims in the README
   were not re-verified in this session.
8. **No independent human review.** Unchanged, and the largest gap.

## G. Where a reviewer should start

If an experienced Go or security engineer has **two to four hours**, spend them
here, in this order.

**P0 — 90 minutes.**

1. **`internal/dnsserver/handler.go` — `Handle` and `clientAllowed`** (~120
   lines). Every query passes through it. Look for: ACL bypass via address
   family, mapped or zoned addresses; whether the single-question restriction
   holds; whether `RcodeRefused` can leak that a name exists. The zone bug
   (F-5) lived here and its shape suggests neighbours.
2. **`internal/policy/engine.go` — `MatchClient` and `prefixContains`** (~60
   lines). Wrong attribution means a client silently gets another network's
   policy. Look for: most-specific-wins under overlapping CIDRs, the catch-all
   selection when several networks have no CIDRs, and whether `MatchNetworkID`
   can be driven by an attacker-chosen token.
3. **`internal/api/auth.go` (403 lines) and `internal/httpx/clientaddr.go`
   (155 lines).** Session handling, and which peers' forwarding headers are
   believed.
   Look for: whether a hostile `X-Forwarded-For` can reach the trusted path
   when `trusted_proxy_cidrs` is empty, and cookie flags under each
   `secure_cookies` mode.

**P1 — 60 minutes.**

4. **`internal/resolver/cache.go`** — key construction. Ask whether two
   different questions can collide on one key, and whether the blocklist
   generation is really part of it.
5. **`internal/blocklist/manager.go`** (661 lines, the largest file on the
   protection path) — feed download, validation and atomic swap. The last-known-good invariant is the
   one to attack: find an input that empties the index instead of keeping it.
6. **`internal/dnsserver/doh.go`** — takes hostile HTTP. Not fuzzed.

**P2 — whatever remains.** `internal/store` migrations and concurrency;
`internal/detect` bounded-memory claims under an adversarial client.

## H. What DNS Daddy can responsibly claim today

**It can say:**

- It is a working forwarding resolver with policy-based filtering over UDP,
  TCP, DoT and DoH, driven by public threat intelligence.
- It refuses to start as an open resolver, and that refusal is asserted by an
  end-to-end test in CI.
- Behavioural detection is alert-only and structurally cannot change an answer.
- A failed, truncated or structurally invalid feed keeps the last known good
  index rather than emptying it.
- It explains its decisions: every block records a category, a source feed and
  a plain-English reason.
- **It can now diagnose its own most common failure**, and says plainly when it
  is running but not serving anyone.
- It runs in well under 1 GB on a single vCPU.
- Its CI runs the race detector, four static analysers, container scanning, an
  SBOM, fuzz smoke runs and an end-to-end smoke test.

**It must not say:**

- Production-ready, enterprise-ready, or audited. No independent adversarial
  review has been done.
- That it validates DNSSEC. It forwards and records the upstream's AD bit,
  which is a weaker statement — and one it already makes correctly.
- That the behavioural detectors have a known false-positive rate. Their
  thresholds are calibrated against synthetic lab traffic.
- That deployment is verified across VM platforms. It is not (§F-1).
- That clean static analysis means the code is secure. It means no rule
  matched.

**Recommended stage: alpha**, moving to beta when a real VM matrix is run and
recorded (§F-1), a Docker Compose deployment is exercised end to end (§F-2),
and at least one independent human review of the §G P0 list is done. Version labels should follow that evidence
rather than lead it.
