# DNS Daddy v0.2.0-alpha.1 — maturation release

*Proposed. Not yet tagged.*

This release is less about adding features and more about making DNS Daddy
dependable and understandable. Most of the work went into finding out where it
was quietly wrong, fixing that, and making it able to explain itself when it
goes wrong again.

The headline is unglamorous: **the documented Docker install refused every
client on a LAN, and reported itself healthy while doing it.** That is fixed,
and so is the more general problem behind it — the resolver had no way to tell
an operator that it was running but not serving anyone.

---

## Fixed

**The documented install refused every LAN client.** `.env.example` shipped an
active `DNSDADDY_ALLOWED_CLIENT_CIDRS=127.0.0.0/8,172.16.0.0/12` under a
heading reading "REQUIRED on a public VPS" — which a LAN operator reasonably
skips, while the line beneath it was live. Since the documented first step is
`cp .env.example .env`, that replaced the built-in ACL with loopback and the
Docker bridge alone. Every client on a LAN or in a VM was answered `REFUSED`
while the dashboard, `/api/v1/health` and the container health check all
reported healthy.

**A network could exist in the dashboard and be unable to resolve, silently.**
Adding a **Network** assigns a policy; it does not permit an address to send
queries — `dns.allowed_client_cidrs` does that, and it is checked first.
Nothing correlated the two, and the counter that proved the problem existed
already and was read by nothing.

**Docker served fewer clients than a native install.** The Compose fallback
was narrower than the binary's own default, silently dropping carrier-grade
NAT (what Tailscale hands out), link-local and all IPv6. Both deployment
artefacts are now pinned to the Go default by test.

**Link-local IPv6 clients were refused, and misattributed where they got
through.** The kernel reports such a peer with a scope zone (`fe80::1%eth0`),
and `netip.Prefix.Contains` returns false for any zoned address — so the
shipped configuration promised to serve exactly the clients it turned away.
RFC 8106 RDNSS, which is how a router advertises a resolver, commonly
advertises a link-local address.

**Upstream health checks proved nothing.** `dnsdaddy doctor` tested upstreams
with a socket connect. On UDP that is a local socket association that succeeds
without a packet leaving the machine, so a silent or absent resolver was
reported as reachable; on TCP it could not see a failed DoT certificate
verification. Upstreams are now probed with a real DNS exchange through the
resolver's own transport.

**Stale threat intelligence could be reported as fresh.** Feed age was measured
from the last refresh *attempt* rather than the last success, so a feed erroring
since Tuesday looked a minute old.

## Added

**`dnsdaddy doctor`.** The first thing to run when DNS is not working — and
before you point anything at the resolver. It reads configuration, reads the
database, and sends real DNS queries at your own listeners and through each
upstream, then reports SYSTEM, DATABASE, DNS LISTENER, CLIENT ACCESS, UPSTREAM,
WEB INTERFACE and THREAT INTELLIGENCE as PASS/WARN/FAIL with the evidence
behind each verdict. It changes nothing, `--json` feeds a monitoring system,
and it exits non-zero so it can gate a deployment.

What it tells apart, which `dig` cannot:

- `REFUSED` means the resolver is running and declining *this source address* —
  not that DNS is broken.
- Nothing listening is a different problem from another process holding the
  port, and that process is named, with systemd-resolved, dnsmasq, BIND,
  Unbound, Pi-hole and CoreDNS each given their own remedy.

**Diagnostics API and dashboard warnings.** `GET /api/v1/diagnostics` returns
the same checks, and the dashboard shows any problem above everything else with
its evidence and the action to take. A resolver that reports itself operational
while refusing every client is no longer possible to miss.

**`dnsdaddy_client_refused_total`** in `/metrics`. A number climbing here rules
out firewalls, routing and port conflicts in one step.

**A reachable LAN dashboard.** `DNSDADDY_DASHBOARD_BIND` publishes the
dashboard on your own network without the loopback-or-nothing choice that
previously pushed people toward `8080:8080`. The default is unchanged, and
plaintext access from a public address is detected and reported.

**A guided Docker installer.** `./deploy/install-docker.sh` checks Docker,
detects the host address, checks ports 53 and 8080, identifies systemd-resolved
without disabling it, asks LAN or VPS, writes `.env`, starts the stack and runs
the readiness check. `--dry-run` shows what it would do.

**First-client onboarding.** The dashboard says when nothing on the network has
used the resolver yet, and gives the command to test one device.

## Security

- **Read-only database inspection.** `doctor` reached the database through a
  path that applied the schema, ran migrations, seeded defaults and switched
  journalling to WAL — so running a newer binary's diagnostic against an older
  live deployment modified it, from the one command that promises to change
  nothing. It now opens strictly read-only.
- **Public plaintext management access is detected.** A management request
  arriving over plain HTTP from a public address is recorded and raised as a
  failure, with instructions that include rotating the admin password.
- **Dependency advisories.** `golang.org/x/mod` updated to v0.40.0 for
  CVE-2026-56864 and CVE-2026-56865.
- **Deployment artefacts pinned by test.** The Compose client ACL must match
  the binary's default, `.env.example` must not ship an active ACL, and the
  dashboard must not be published on every interface.

## Known limitations

Stated plainly, because they bound what this release is good for.

- **No independent professional security review.** Nobody outside the project
  has adversarially reviewed the DNS parser, the resolver, policy attribution
  or the authentication code. This is the largest gap and no amount of CI
  substitutes for it.
- **The deployment matrix has not been executed.** Every row in
  [docs/deployment-matrix.md](../deployment-matrix.md) is marked *not run*.
  Docker, native, five VM networking arrangements and a public VPS all need
  someone to run them on real hardware and record what happened.
- **Pi-hole coexistence is analysed, not measured.** The reasoning is traceable
  to the code; neither topology has been deployed end-to-end.
- **Behavioural detectors have no measured real-world false-positive rate.**
  Their thresholds come from synthetic lab traffic. They are alert-only for
  exactly this reason.
- **DNSSEC is not validated locally.** DNS Daddy records the upstream's verdict,
  which a lying upstream can fake.

## Upgrading

No configuration changes are required and no migration is needed. Two things
are worth doing after upgrading:

```bash
docker compose pull && docker compose up -d
docker compose exec dnsdaddy dnsdaddy doctor
```

If `doctor` reports a client-access failure, it is telling you about a
misconfiguration that was already there and previously invisible.

If your `.env` still contains an active `DNSDADDY_ALLOWED_CLIENT_CIDRS` copied
from the old `.env.example`, and you are on a LAN, delete the line — the
built-in default covers every private range.
