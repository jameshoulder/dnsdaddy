# Lab: DGA simulation

**Client:** 172.30.0.36 (`127.0.0.7` when run natively) ·
**Expected finding:** `dga_like_domains`, medium severity ·
**ATT&CK:** [T1568.002]

```bash
bin/dnsdaddy-lab -server 127.0.0.1:5353 -scenario dga-simulation -speed 10
```

## Objective

Show what a domain generation algorithm looks like from the resolver, and be
precise about how much a surface-statistics heuristic can and cannot tell you.

## What is simulated

A host working through a candidate list: many unrelated registered domains,
random-looking second-level labels, rotating top-level domains, nearly all
failing.

```
qzbxkvnmrtwp.example      NXDOMAIN
hjkxzqvwmnbt.test         NXDOMAIN
vbnmqxzkwrth.example      NXDOMAIN
kqxzvwbnmrtjd.test        NXDOMAIN
```

About 530 lookups over eleven simulated minutes.

Malware using a DGA computes candidate domains from a seed — usually the
current date — and tries them until one answers. The operator registers only
one or two, so the resolver sees a host asking for hundreds of unrelated
domains and failing nearly all of them.

A real DGA rotates `.com`, `.net`, `.info`, `.biz`, `.top`. The lab uses only
`.example` and `.test`, because using the real ones would mean querying names
somebody could actually register.

## How the heuristic works

Each *distinct registered domain* the client resolves has its second-level
label scored on four surface statistics, equally weighted:

| Property | Why |
|---|---|
| Vowel distribution | Written English runs 25–50% vowels among letters. A uniform draw runs much lower. |
| Longest consonant run | `qzbxkv` is not a word. Runs of 5+ are rare in language and common in generated strings. |
| Digit fraction | Many generators mix digits in. Brand names rarely do. |
| Per-character entropy | Measured only on labels of 12+ characters, where it means something. |

A label scoring ≥0.45 counts as a candidate. `cloudflare` trips none of the
four; `qzbxkvnmrtwp` trips three.

Then the client is scored on the candidates:

| Signal | Measured | Band | Contributed |
|---|---|---|---|
| `algorithmic_domain_count` | ~340 | 8 – 60 | 0.40 |
| `mean_randomness` | ~0.62 | 0.45 – 0.80 | ~0.12 |
| `candidate_nxdomain_ratio` | ~0.97 | 0.30 – 0.90 | 0.25 |
| `distinct_tlds` | 2 | 2 – 8 | 0.00 |

The NXDOMAIN ratio is computed **only over the candidate domains**, not over
all the client's traffic. Mixing in ordinary browsing would wash out the very
signal being measured.

## What this heuristic cannot do

Stated plainly, because the alternative is implying coverage that is not there:

**It will not detect a word-list DGA.** Some families generate pronounceable
domains by combining dictionary words — `silverhorse.com`, `quietriver.net`.
Those score near zero on all four properties. This approach misses them
completely. Detecting them is a research problem, and it is on the roadmap
rather than claimed here.

**It is not machine learning and is not described as such.** There is no model,
no training data, and no learned representation. It is four arithmetic
measurements combined with equal weights. Calling that "AI-powered detection"
would be marketing, and it would make the output less trustworthy, not more,
because nobody could check it.

**Internationalised domains are excluded.** Punycode (`xn--`) is
machine-generated by definition and would score like a DGA every time.

## False-positive considerations

- **Cloud and SaaS hostnames** frequently contain generated identifiers. The
  common CDN and cloud providers are excluded; a vendor yours uses may not be.
- **URL shorteners and advertising infrastructure** use short random-looking
  registered domains as their normal business.
- **Security tooling** that resolves generated names deliberately — including
  this lab.

The `candidate_nxdomain_ratio` signal is what usually separates these: a SaaS
vendor's generated hostnames *resolve*, and a DGA's candidates mostly do not.

## Investigation steps

1. **Look at the example domains** in the finding's evidence. A DGA produces
   names with a consistent length and character-set fingerprint — that
   consistency is often more recognisable than the randomness.
2. **Check registration dates for any candidate that resolved.** That one is
   the rendezvous point, and it is usually days old.
3. **Correlate with `nxdomain_burst`** for the same client and window. In this
   scenario both fire, and they are independent measurements of the same
   behaviour.
4. **Check the schedule.** Date-seeded algorithms restart, so the pattern
   recurs at intervals.
5. **Treat a confirmed match as an infected endpoint.** The resolver sees the
   symptom; the host has the cause.

## Mitigation

Block any candidate domain that *did* resolve — that is live infrastructure.
Blocking the ones that failed achieves nothing; tomorrow's list is different by
design.

The durable answer is on the endpoint, not in the resolver.
